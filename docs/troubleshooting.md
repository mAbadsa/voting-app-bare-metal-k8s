# Troubleshooting Log

Real problems hit while building a 3-node Kubernetes cluster (kubeadm +
containerd + Calico on Multipass VMs) and deploying the voting app on it.
Each case shows the output captured at the time, what caused it, and
how it was fixed.

> **About the captured output:** shell prompts are shortened to `$` and
> long repeated log lines are trimmed (marked `...`). Nothing else was
> edited. Join tokens and credentials are not included.

## Phase 1: Cluster bootstrap

### 1. `kubeadm init` cannot connect to the container runtime

**Symptom**
```
$ sudo kubeadm init
[preflight] Some fatal errors occurred:
        [ERROR CRI]: could not connect to the container runtime: ... dial unix /var/run/containerd/containerd.sock: connect: no such file or directory
```

**Diagnosis**
```
$ systemctl status containerd
Unit containerd.service could not be found.
```

**Cause:** containerd was not installed, so there was no socket for kubeadm to talk to.

**Fix:** install containerd, generate its config, switch it to the
`systemd` cgroup driver (so it matches kubelet), load the `overlay` and
`br_netfilter` modules, set the bridge/forwarding sysctls, and disable swap.
```bash
sudo apt install -y containerd
sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
sudo systemctl enable --now containerd
```

**Lesson:** kubeadm's preflight checks name the missing prerequisite. Read them before changing anything.

### 2. containerd restart-loops after install

**Symptom**
```
$ sudo systemctl start containerd
Job for containerd.service failed because the control process exited with error code.

$ systemctl status containerd.service
     Active: activating (auto-restart) (Result: exit-code) since Mon 2026-09-14 15:31:33 IDT; 3s ago
    Process: 14798 ExecStart=/usr/bin/containerd (code=exited, status=1/FAILURE)

$ journalctl -xeu containerd.service
Sep 14 15:31:01 controll-panel containerd[14725]: containerd: failed to load TOML from /etc/containerd/config.toml: expected containerd config version equal to or less than `3`, got `4`
Sep 14 15:31:06 controll-panel systemd[1]: containerd.service: Scheduled restart job, restart counter is at 66.
```

**Diagnosis**
```
$ containerd --version
containerd github.com/containerd/containerd/v2 v2.3.5 1294c24a7da8e5a793ed378161673abe94118892
$ which containerd
/usr/local/bin/containerd
$ dpkg -l | grep -i containerd
ii  containerd   2.2.2-0ubuntu1.1   amd64   daemon to control runC
```

**Cause:** two containerd binaries were on the machine. A leftover
v2.3.5 in `/usr/local/bin` came first on `$PATH`, so
`containerd config default` wrote a version-4 config. The systemd unit
runs `/usr/bin/containerd` (v2.2.2 from apt), which only reads config
versions up to 3, so it refused to start.

**Fix:** remove the stray binary and regenerate the config with the
binary systemd actually runs.
```bash
sudo rm /usr/local/bin/containerd
hash -r
containerd config default | sudo tee /etc/containerd/config.toml
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
sudo systemctl restart containerd
```

**Lesson:** "the command works" is not the same as "the right binary is running."
Check `which -a`, `--version`, and the `ExecStart=` line in the unit file.

### 3. `kubeadm init` times out waiting for the control plane

**Symptom**
```
[kubelet-start] Starting the kubelet
error: error execution phase wait-control-plane: cannot obtain client without bootstrap: could not bootstrap the admin user in file admin.conf: unable to create ClusterRoleBinding: context deadline exceeded
```

**Evidence from the kubelet log**
```
kubelet[24448]: E0919 12:29:33.527387 remote_runtime.go:325] "RunPodSandbox from runtime service failed" err="rpc error: code = Unknown desc = failed to start sandbox ...: failed to create containerd task: failed to start shim: start failed: failed to create TTRPC connection: unsupported protocol: \b\x03\x12Yunix"
kubelet[24448]: E0919 12:29:33.536756 kubelet.go:3596] "Unable to register mirror pod because node is not registered yet" err="node \"controll-panel\" not found"
```
The API server's static pod could not start because the container
runtime failed to create its sandbox, so the node never registered.

`crictl` also failed when run without `sudo`:
```
$ crictl ps -a
ERRO[0000] validate service connection: ... dial unix /run/containerd/containerd.sock: connect: permission denied
```

**Checking for more leftover binaries**
```
== ctr ==
/usr/local/bin/ctr
/usr/bin/ctr
/bin/ctr
```
(`/bin` and `/usr/bin` are the same directory on Ubuntu. The only real
duplicate was `ctr` in `/usr/local/bin`.)

**Cause:** not isolated. The failure was in the runtime's shim layer on
a machine that still had leftovers from an earlier manual containerd
install. After removing the leftovers and doing a clean reset, init
completed.

**Fix**
```bash
sudo rm -f /usr/local/bin/ctr && hash -r
sudo kubeadm reset -f
sudo systemctl stop kubelet containerd
sudo rm -rf /etc/cni/net.d /var/lib/cni /var/lib/etcd
sudo systemctl start containerd
sudo kubeadm init
```

**Lessons**
- Always reset (`kubeadm reset -f`) between failed init attempts. Half-completed state causes confusing follow-on errors.
- `crictl` needs `sudo` to reach the containerd socket.

### 4. `kubectl` on a worker node: connection refused

**Symptom**
```
ubuntu@node-1:~$ kubectl exec -it test-nginx -- curl -s localhost
E0919 13:37:02.331769   31070 memcache.go:381] "Couldn't get current server API group list" err="Get \"http://localhost:8080/api?timeout=32s\": dial tcp [::1]:8080: connect: connection refused"
The connection to the server localhost:8080 was refused - did you specify the right host or port?
```

**Cause:** the admin kubeconfig was only copied to `~/.kube/config` on the
control plane. Without a kubeconfig, `kubectl` falls back to
`localhost:8080`. Nothing is wrong with the cluster.

**Fix:** run `kubectl` from the control plane. Workers run `kubelet`,
which has its own credentials (`/etc/kubernetes/kubelet.conf`) and does
not need `kubectl`.

### 5. `calico-node` stuck at `Init:2/3`

**Symptom**
```
calico-node-5h2cz   0/1   Init:2/3   0   6m25s
```

**Evidence**
```
Normal  Scheduled  10m    default-scheduler  Successfully assigned kube-system/calico-node-5h2cz to node-2
Normal  Pulled     4m13s  kubelet            spec.initContainers{upgrade-ipam}: Successfully pulled image "docker.io/calico/cni:v3.28.0" in 5m39.219s (5m39.22s including waiting). Image size: 94536228 bytes.
Normal  Pulling    4m10s  kubelet            spec.initContainers{mount-bpffs}: Pulling image "docker.io/calico/node:v3.28.0"
```

**Cause:** a 94 MB image took 5m39s to pull on node-2, so the init
containers progressed slowly. Nothing was misconfigured.

**Fix:** waited. All three nodes reached `Ready`.

**Lesson:** read the `Events` section of `kubectl describe pod`. The pull
timestamps showed a slow network, not a CNI problem.

## Phase 2: Networking

### 6. Reaching a pod: `curl localhost` and `curl <ClusterIP>:<NodePort>` fail

**Symptom**
```
$ curl -I http://localhost
curl: (7) Failed to connect to localhost port 80 after 0 ms: Could not connect to server

$ kubectl get svc ex-nginx-svc
NAME           TYPE       CLUSTER-IP     EXTERNAL-IP   PORT(S)        AGE
ex-nginx-svc   NodePort   10.103.16.22   <none>        80:30765/TCP   6s

$ curl 10.103.16.22:30765      # did not work
```

**Cause**
- A pod has its own IP on the CNI network. `localhost` on the node is a different network namespace. (`kubectl exec <pod> -- curl localhost` works because it runs inside the pod.)
- The ClusterIP listens on the Service port (`80`), not the NodePort. The NodePort is opened on each node's own IP.

**Fix**
```bash
curl http://10.103.16.22:80          # ClusterIP + service port (from inside the cluster)
curl http://<node-ip>:30765          # node IP + NodePort
kubectl port-forward pod/test-nginx 8080:80   # quick one-off test
```

## Phase 3: Deploying the app

### 7. `namespaces "voting-app" not found`

**Symptom**
```
Error from server (NotFound): error when creating "deployments/postgres-deployment.yaml": namespaces "voting-app" not found
Error from server (NotFound): error when creating "deployments/redis-deployment.yaml": namespaces "voting-app" not found
...
```

**Cause:** the manifests were reorganized into folders and applied
without a `Namespace` object. `namespace: voting-app` in a resource's
metadata only says where to put it. It does not create the namespace.

**Fix:** add a `namespace.yaml` and apply it first.
```bash
kubectl apply -f namespace.yaml
kubectl apply -f deployments/
```

### 8. `ImagePullBackOff` on every app pod

**Symptom**
```
result-deployment-54585cd4dc-6f58b     0/1     ImagePullBackOff   0   3m49s   192.168.84.137   node-1
vote-deployment-6bbfb968fb-82ttc       0/1     ImagePullBackOff   0   3m58s   192.168.84.140   node-1
worker-deployment-5ddbc5b4d-xb2j2      0/1     ErrImagePull       0   4m46s   192.168.247.14   node-2
```

**Cause:** the Wi-Fi connection that the VMs use was down, so no node
could reach the registry. The manifests were fine.

**Fix:** restore connectivity. Kubernetes retries pulls with exponential
backoff, and the pods recovered on their own.

**Lesson:** `kubectl describe pod` shows the actual pull error. Rule out
image names and credentials before suspecting the cluster network.

### 9. `FailedScheduling: Insufficient cpu`

**Symptom**
```
Warning  FailedScheduling  21m  default-scheduler  0/3 nodes are available: 1 Insufficient cpu, 2 node(s) had untolerated taint(s). preemption: 0/3 nodes are available: 1 No preemption victims found for incoming pod, 2 Preemption is not helpful for scheduling.
```

**Cause:** the control plane carries the default `NoSchedule` taint, so
only the two 2-vCPU workers could run pods. With too many replicas, one
worker ran out of CPU.

**Fix:** scale the Deployments down to 2 replicas, and set the same
value in the manifests so a later `apply` doesn't scale them back up.
```bash
kubectl scale deployment vote-deployment --replicas=2 -n voting-app
kubectl scale deployment result-deployment --replicas=2 -n voting-app
kubectl describe nodes | grep -A5 "Allocated resources"
```

**Lesson:** the taint on the control plane is intentional. The fix was
adjusting workload to capacity. Resource requests and limits on each
Deployment would make this kind of failure easier to predict.

### 10. Pods do not return to a node after it recovers

After stopping `node-1` and bringing it back, every pod was running on `node-2`:

```
postgres-deployment-5976d75c4b-6t6mk   1/1   Running   0   34m   192.168.247.18   node-2
redis-deployment-67dd7748c5-psf8b      1/1   Running   0   27m   192.168.247.21   node-2
result-deployment-54585cd4dc-gn9fm     1/1   Running   0   27m   192.168.247.23   node-2
vote-deployment-6bbfb968fb-cphjv       1/1   Running   0   34m   192.168.247.20   node-2
worker-deployment-5ddbc5b4d-8swtc      1/1   Running   0   27m   192.168.247.24   node-2
```

**Cause:** expected behavior. When `node-1` failed, its pods were
recreated on `node-2`. The scheduler only places pods when they are
created, so it does not move running pods back when capacity returns.
Kubernetes self-heals but does not self-balance.

**To redistribute:** trigger new scheduling (scale a Deployment up and
back down, delete a pod, or `kubectl drain` and `uncordon` a node).

## Phase 4: Monitoring

### 12. `helm install` of kube-prometheus-stack times out

**Symptom**
```
$ helm install monitoring prometheus-community/kube-prometheus-stack --namespace monitoring
Error: INSTALLATION FAILED: failed pre-install: 1 error occurred:
	* timed out waiting for the condition

$ helm install monitoring prometheus-community/kube-prometheus-stack --namespace monitoring
Error: INSTALLATION FAILED: cannot re-use a name that is still in use
```

**Cause:** the first install stopped at a pre-install hook, probably
because of limited CPU on the 2 vCPU nodes. It left a failed release
behind, so Helm refused to reuse the name.

**Fix:** remove the failed release, then reinstall with a longer
timeout, smaller resource requests, and the admission webhooks disabled.
```bash
helm uninstall monitoring --namespace monitoring
helm install monitoring prometheus-community/kube-prometheus-stack \
  --namespace monitoring --timeout 10m \
  --set prometheus.prometheusSpec.resources.requests.cpu=100m \
  --set prometheus.prometheusSpec.resources.requests.memory=256Mi \
  --set grafana.resources.requests.cpu=50m \
  --set grafana.resources.requests.memory=128Mi \
  --set alertmanager.enabled=false \
  --set kubeStateMetrics.enabled=false \
  --set prometheusOperator.admissionWebhooks.enabled=false
```
The install reported `STATUS: deployed`. An `admission-patch` pod
crash-looped for several minutes and was gone from the final listing
(not investigated further):
```
NAME                                                   READY   STATUS    RESTARTS   AGE
monitoring-grafana-6fc7b9fbfd-h67t6                    3/3     Running   0          10m
monitoring-kube-prometheus-operator-7685c6b5b8-452bg   1/1     Running   0          10m
monitoring-prometheus-node-exporter-2k2f9              1/1     Running   0          10m
monitoring-prometheus-node-exporter-99thj              1/1     Running   0          10m
monitoring-prometheus-node-exporter-xrs97              1/1     Running   0          10m
prometheus-monitoring-kube-prometheus-prometheus-0     2/2     Running   0          9m15s
```

**Trade-off:** Alertmanager, kube-state-metrics, and the admission
webhooks are disabled to fit the VM size. That is acceptable for a lab
but not for production.

## Phase 5: Application connectivity

### 13. `curl: (35) wrong version number`

```
$ curl -I https://10.132.6.165:31000/
curl: (35) OpenSSL/3.0.13: error:0A00010B:SSL routines::wrong version number
```

**Cause:** the vote app serves plain HTTP. Using `https://` makes curl
attempt a TLS handshake against a non-TLS port.

**Fix:** `curl -I http://<node-ip>:31000/`

### 14. worker and result stuck on "Waiting for db"

**Symptom** (all deployments showed `Running`, `1/1`)
```
$ kubectl logs deploy/worker-deployment -n voting-app --tail=30
Waiting for db
Waiting for db
Waiting for db
...
```

**Cause:** the app images look up the database by the hostname `db`. The
Postgres Service was named `postgres`, so the name never resolved. A pod
can be `Running` while a dependency is unreachable.

**Fix:** rename the Service to `db` in the manifest and sync it.
```yaml
metadata:
  name: db
  namespace: voting-app
```
```bash
kubectl get endpoints db -n voting-app    # should list the postgres pod on 5432
```
Afterwards:
```
$ kubectl logs -n voting-app worker-deployment-5ddbc5b4d-zghrh --tail=30
Connected to db
Found redis at 10.109.156.249
Connecting to redis
Processing vote for 'a' by 'fd6cffa5eb34b6f'
```

**Lessons**
- A Service's name is its DNS name, so a name the app hard-codes must match.
- Readiness probes would have kept these pods out of `Ready` while the dependency was unreachable.

### 15. `relation "votes" does not exist`

**Symptom**
```
$ kubectl logs deploy/result-deployment -n voting-app
App running on port 80
Waiting for db
...
Connected to db
Error performing query: error: relation "votes" does not exist
Error performing query: error: relation "votes" does not exist
...
```

**Cause:** the result app connected to Postgres before the `votes`
table existed. The worker creates the table when it first connects.
Once the worker logged `Connected to db` and `Processing vote` (see
case 14), the table was in place.

**Note on persistence:** Postgres in this cluster has no PVC, so its data
is lost if the pod restarts. In that case the worker and result pods need
to reconnect, and the table is recreated.

## Debugging checklist

The order that found most of the problems above:

```bash
kubectl get nodes
kubectl get pods -A -o wide
kubectl describe pod <pod> -n <ns>              # read the Events section first
kubectl logs <pod-name> -n <ns>                 # use a specific pod, not deploy/...
kubectl get endpoints <svc> -n <ns>             # does the Service have backends?
kubectl describe nodes | grep -A5 "Allocated resources"
journalctl -u kubelet -n 100 --no-pager         # on the node
journalctl -u containerd -n 100 --no-pager
which -a <binary> && <binary> --version         # which binary is actually running?
```
